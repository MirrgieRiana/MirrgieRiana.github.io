# protocol-105

## 開発

### ソースコード上のコメント

ここでは、ソースコードや設定ファイルなどに、コメント構文として記述されるコメントを扱います。

一般に、説明対象の具体的な利用先を挙げるべきではありません。
その対象に新しい利用先が増えた場合に、そのコメントは非網羅的で不正確な記述となります。

### 更新情報

#### 迂回的更新情報の禁止に関する一般論

本セクションの内容は一般論であり、情報媒体ごとの個別のルールが存在する場合は、そちらが優先されます。
PR 説明文は、本セクションの対象ではありません。

一般論として、更新情報というものは、読み手にとって最後の状態からの、読み手にとって可視である差分を記述するものです。
何を以って読み手にとって可視であるかの基準は、その更新情報が記述される媒体によって異なります。

読み手にとって可視でない、内部的な変更は、記述するべきではありません。

読み手にとって最後の状態以降に出現し、読み手の前に現れることなく廃止された、一時的な中間状態の存在は、示唆するべきではありません。
例えば、「醤油コロッケを追加」と「醤油コロッケをソースコロッケに変更」が同一の更新情報内に記述されるのは、迂回的で、不適切です。
醤油コロッケは結局プレイヤーの目に入ることなく消えた中間状態であるため、代わりに、「ソースコロッケを追加」と直線的に記述すべきです。

### git / GitHub

#### 差分の説明

自動生成物とその元のファイルが対応して編集されている場合、生成物側は、生成物であるとだけ説明してください。

#### デフォルトブランチへの push の禁止

デフォルトブランチへの push は、いかなる場合であっても、厳禁です。

#### PR

PR にコミットを push した際には、状況の変化に応じて、PR 説明文ないしタイトルを更新しなければなりません。

#### 論理コンフリクト

PR のコンフリクトには、物理コンフリクトだけでなく、物理的にはマージ可能でも実際には不条理を持ち込んでいる、論理コンフリクトがあります。
例えば、片方がすべての ctx 変数を context に改名し、別のブランチが ctx を持った関数を追加すると、リファクタリング退行が起こります。

これを防ぐには、比較対象の 2 個のブランチの共通祖先から、それぞれどのような意図を適用したのかを、意味論的に洞察する必要があります。

#### PR の作成

アイデアを PR にする際には、次の手順に従ってください。

1. 現在のアイデアが、どのリビジョンに基づいているかを確認します。
2. リモートからマージ対象のブランチの最新の状態を pull します。
3. マージ対象のブランチの変化分を確認し、現在のアイデアが受ける影響を分析し、適宜、退行を持ち込まないようにアイデアを修正します。
4. マージ対象のブランチの最新のリビジョンから、新しいブランチを作成し、コミットします。
   - コミットは、極力、フォーマット差分、リファクタリング差分、挙動の変更を、分けてコミットするべきです。
   - 1 個のコミットには、極力、1 個の関心事があるべきです。
5. ブランチを push します。
6. 以下の条件で、PR を作成します。
   - タイトルや説明文は、リポジトリに指示文があればそれに従い、そうでない部分は、既存の PR の様式に一貫させてください。
      - 複数の様式がある場合は、「リポジトリの所有者＞指示を出したユーザー以外＞指示を出したユーザー」の順で優先してください。
   - Draft 属性を付与してください。
   - その指示を出したユーザーをアサインしてください。

---

PR を作成する際は、できるだけ、1 個のテーマに分割し、そのテーマに無関係な差分は持ち込まないべきです。
バグの修正のついでにフォーマットを整形したり、構造や変数名を無意味に変更したり、無関係な部分のコメント文を推敲してはいけません。
