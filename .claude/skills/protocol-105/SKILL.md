# protocol-105

スキルの再取得が命令された際は、その更新分を熟読した事実の報告だけでなく、前回の熟読から変化した箇所も述べなければなりません。

## 作業

### 拡大解釈による命令の捏造の禁止

**あなたは、ユーザーの以下の発言が、あなたへの改変操作の命令ではないことを、十分に理解しなければなりません。**

- 質問
- 願望の共有
- 不満の表明
- 問題の追及

**これらの発言をあなたへの命令と勝手に解釈し、ユーザーの意に反した改変操作を行うことは、重大な破壊行為に他なりません。**
**言うまでもなく、極めて有害な行動であるため、あなたは、このような拡大解釈による命令の捏造を、決して行ってはいけません。**

### ユーザーの命令外の改変操作の禁止

**あなたは、いかなる状況や背景があろうとも、ユーザーが明示的かつ直接的に許可していない限り、いかなる改変操作もしてはいけません。**

ユーザーの許可の文言内で明示されず、指示語や、あなたの解釈によって補完し、必要であると判断した改変操作は、明示的な許可ではありません。

ユーザーの許可の文言に直接的に含まれず、各種ルールや状況によって、間接的に必要となる改変操作は、直接的な許可ではありません。
ルールによって、作業の一部としてユーザーの命令外の改変操作に当たる手順が定義されている場合も、その手順への直接的な許可ではありません。
この唯一の例外は、ルール上で、「～の命令は～を含意する」のように、随伴性を命令自体の含意によって定義している場合です。

改変操作とは、「会話の外部の状態を変化させない操作、および、それに付随するキャッシュや履歴の変化」を除く、ありとあらゆる操作を指します。
あなたの通常の手段による発言、あなた専用に確保された作業領域、および会話の場に紐づいたその他の固有のリソースは、会話の内部として扱います。

各種ルールや状況によって、ユーザーの命令外の改変操作が必要になる場合は、それを独断で強行する代わりに、ユーザーに報告しなければなりません。
既に実行してしまった操作に付随して、ユーザーの命令外の改変操作が実は必要であったことが判明した場合も、同様です。

## 開発

### 普遍的なルール

このセクションの対象は、プログラムか自然言語かを問いません。

リポジトリの内容を変更もしくは追加する際は、必ず、既存の類似の部分を探し、記述スタイルを厳密に一貫させなければなりません。
記述スタイルは、フォーマット、スペーシング、改行、空行、命名規則、文体、語彙選択、言い回し、ファイル構造、順序など、様々です。
そのために、まず、どこを見れば既存の記述スタイルを参考にできるかを、考察しなければなりません。
類似性の粒度も様々で、プログラムという広い概念の類似、言語の類似、実装対象の類似、用途の類似など、様々です。
あなたが完全に自己流のスタイルで書いてよいのは、参考にすべきリポジトリそのものがまだない場合のみです。
そのような場合でも、既存の類似の部分の調査自体を省略してよいことにはなりません。
あなたが作ったスタイルの壊れた成果物を修正するだけのために、余計な工程を踏ませないでください。

新しい項目を追加する際には、検討もなしに、今見えている場所にとりあえず追加してはいけません。
既存の部分と調査して、その項目が真に属すべき場所を、合理的に検討しなければなりません。

新しい項目を追加する際には、検討もなしに、既存部分の先頭や末尾に追加してはいけません。
既存の部分と比較して、真に挿入すべき位置を、一貫したルールに基いて、合理的に検討しなければなりません。

### ソースコード上のコメント

ここでは、ソースコードや設定ファイルなどに、コメント構文として記述されるコメントを扱います。

一般に、コメント内で、説明対象の具体的な利用先を挙げるべきではありません。
その対象に新しい利用先が増えた場合に、そのコメントは非網羅的で不正確な記述となります。

### 更新情報

#### 迂回的更新情報の禁止に関する一般論

本セクションの内容は一般論であり、情報媒体ごとの個別のルールが存在する場合は、そちらが優先されます。
PR 説明文は、本セクションの対象ではありません。

一般論として、更新情報というものは、読み手にとって最後の状態からの、読み手にとって可視である差分を記述するものです。
何を以って読み手にとって可視であるかの基準は、その更新情報が記述される媒体によって異なります。

読み手にとって可視でない、内部的な変更は、記述するべきではありません。

読み手にとって最後の状態以降に出現し、読み手の前に現れることなく廃止された、一時的な中間状態の存在は、示唆するべきではありません。
例えば、「醤油コロッケを追加」と「醤油コロッケをソースコロッケに変更」が同一の更新情報内に記述されるのは、迂回的で、不適切です。
醤油コロッケは結局プレイヤーの目に入ることなく消えた中間状態であるため、代わりに、「ソースコロッケを追加」と、直線的に記述すべきです。

### テストコード

テストコードが守るべき中心的な対象は、善意で書かれた自然なコードの改善や応用が、新たなバグを持ち込むことです。
逆に言えば、その仕組みを壊そうとする明確な悪意を持たなければ到底踏まないような経路は、テストで守る優先度は下がることになります。

## git / GitHub

### 差分の説明

自動生成物とその元のファイルが対応して編集されている場合、生成物側は、生成物であるとだけ説明し、詳細を省いてください。

### ブランチ

あなたは、たとえユーザーによる明示的かつ直接的な命令があったとしても、決して、デフォルトブランチに対して push をしてはいけません。
不可逆的な事故を防ぐため、これにはいかなる例外もありません。

新しいブランチを作成する際は、リモートのブランチを指定すると、自動的に upstream がそれに設定されることに注意してください。
例えば、`git switch -c branch1 origin/main` のようなコマンドを打つと、branch1 の表示で main に push される地雷が作成されます。

#### 論理コンフリクト

ブランチのコンフリクトには、物理コンフリクトと、論理コンフリクトがあります。
論理コンフリクトとは、物理的にはマージ可能と判定されているものの、論理的、意味論的な不整合を持っている、といった状態です。
例えば、片方がすべての ctx 変数を context に改名し、別のブランチが ctx を持った関数を追加すると、両者は論理コンフリクトの状態になります。
なぜなら、それらをマージすると、改名のリファクタリングが部分的に退行し、リポジトリが不整合な状態になるからです。

これを防ぐには、比較対象の 2 個のブランチの共通祖先から、それぞれどのような意図を適用したのかを、意味論的に洞察する必要があります。

### PR

PR の作成の命令は、当該 PR のためのコミットおよび push を含意します。

PR の作成者が bot かあなたが使用しているユーザーのアカウントである場合、push の命令は、PR のタイトルと説明文の更新も含意します。

PR は、ユーザーからマージ先を明示的に指定されない限り、常にデフォルトブランチをマージ先として実装しなければなりません。

#### PR の作成

アイデアを PR にする際には、次の手順に従ってください。

1. 現在のアイデアが、どのリビジョンに基づいているかを確認します。
2. リモートからマージ対象のブランチの最新の状態を pull します。
3. マージ対象のブランチの変化分を確認し、現在のアイデアが受ける影響を分析し、適宜、退行を持ち込まないようにアイデアを修正します。
4. マージ対象のブランチの最新のリビジョンから、新しいブランチを作成し、コミットします。
   - コミットは、極力、フォーマット差分、リファクタリング差分、挙動の変更を、分けてコミットするべきです。
   - 1 個のコミットには、極力、1 個の関心事があるべきです。
5. ブランチを push します。
6. 以下の条件で、PR を作成します。
   - タイトルや説明文は、リポジトリに指示文があればそれに従い、そうでない部分は、既存の PR の様式に一貫させてください。
      - 複数の様式がある場合は、「リポジトリの所有者＞命令を出したユーザー以外＞命令を出したユーザー」の順で優先してください。
   - Draft 属性を付与してください。
   - その命令を出したユーザーをアサインしてください。

---

PR を作成する際は、できるだけ、1 個のテーマに分割し、そのテーマに無関係な差分は持ち込まないべきです。
バグの修正のついでにフォーマットを整形したり、構造や変数名を無意味に変更したり、無関係な部分のコメント文を推敲してはいけません。

#### push に付随する CI の監視

あなたに CI の待機のための合理的な手段が与えられている場合、push に伴う CI の監視と結果の分析も、あなたの作業の一部です。
逆に、CI の待機のための合理的な手段が与えられていない場合は、CI の監視を試みてはいけません。
