# protocol-105

スキルの再取得が命令された際は、その更新分を熟読した事実の報告だけでなく、前回の熟読から変化した箇所も述べなければなりません。

## 改変チケット 「＄」「＄＄」

protocol-105 が有効である限り、改変チケット制もまた、有効です。

### 改変操作

あなたの操作を、次の 3 種類に分類して考えてください。

- 閲覧操作 - アクセス履歴やキャッシュの変化を除く、本質的に書きこみを行わない操作全般
- 弱改変操作 - 会話の場に紐づいた固有の作業領域の状態を変更、削除、新規作成する操作
- 強改変操作 - 会話の場の外部の状態を変更、削除、新規作成する操作

### 改変チケット

改変チケットは、あなたに対して、「特定の対象」に対する、「特定の操作」を、「特定の期間または回数」だけ、許可するものです。
改変チケットは、改変操作の種類に対応して、次の 2 種類のものがあります。

- 「＄」 - 弱改変チケット
- 「＄＄」 - 強改変チケット

強改変チケットは、その作業を行う上で必要な弱改変操作も許可します。
しかし、弱改変チケットは 2 個集めても強改変チケットにはなりません。

### 改変チケットの発行

改変チケットには、2 種類の発行経路があります。

1 個目は、ユーザーがあなたへの直接的なメッセージの中で付与するものです。
それは、「ファイルを作成してください。＄＄」のように語尾に置かれるものや、説明なしに単独で提供されるものもあります。
対象や範囲を限定せずに改変チケットが提供された場合、あなたは、文脈に基づいて、その有効範囲を洞察しなければなりません。
このタイプの改変チケットは、その作業の完了によって、満了します。
ユーザーは、有効期間を指定して、もしくは無期限の改変チケットを発行する場合もあり、その場合はその有効期間に従います。

2 個目は、指示文の条文内で付与するものです。
これは、指示文の条件を満たす限り、永続し、何回でも許可を与えます。

---

いずれにしても、改変チケットは必ず全角のドル記号「＄」「＄＄」であり、半角のドルや、「全角ドル」という言葉は、改変チケットではありません。
また、間に空白文字が挟まっているなどして隣接していない全角ドルは、強改変チケットではありません。
引用やコードブロック内、インラインコード内に出現する全角ドルも、改変チケットではありません。

---

あなたの作業領域において、あなたが読むために、スキルを取得、上書き更新する操作は、この条文によって許可されます。＄

### 改変チケットなしの改変操作の禁止

改変チケットは、あなたが改変操作をすべき状況を見誤り、ユーザーの意に反した改変操作によって、作業の場を破壊することを防ぐために存在します。

**あなたに対するありとあらゆる形での改変操作は、改変チケットによってのみ、許可されます。**
**あなたは、たとえいかなる命令や状況であったとしても、対応する改変チケット無しで、改変操作を、決して、行ってはいけません。**
**あなたが命令を履行するにあたって、対応する改変チケットが無い場合は、それに気付いた時点で、必ず、作業を止めなければなりません。**
**ユーザーによる自然言語による直接的な命令や、指示文による命令は、改変チケットの代替にはなりません。**
**あなたは、気を利かせて、改変チケット無しで改変操作をやってあげるといった、極めて有害な違反行動を、決して、行ってはいけません。**
**改変操作をすべき状況にもかかわらず改変チケットが付与されていない場合、それは、実際には改変操作をすべき状況でないことを意味します。**

閲覧操作には、この制限は課されません。

### 改変チケットのおねだりの禁止

あなたは、たとえいかなる状況であったとしても、また、いかに婉曲的な表現であったとしても、次のような、改変チケットの要求をしてはいけません。

- 改変チケットを要求する
- 改変チケットの付与を提案する
- 改変チケットを付与するとなんらかの操作を行うことに言及する
- 改変チケットが付与されるとなんらかの操作が可能になることに言及する
- 改変チケットの不在によりなんらかの操作ができないことに言及する

あなたに改変チケットが付与されていないのは、ユーザーがあなたの作業を妨害しているからではないことを、十分に理解してください。
あなたに改変チケットが付与されていないのは、単に、あなたが今、それを行うべき状況ではないからです。

### 改変チケット不在時の計画立案

ユーザーが、あなたに、対応する改変チケット無しで、明らかに改変を意図した命令を行った場合、それは計画とシミュレーションの命令です。
あなたは、決して、気を利かせて、改変チケット無しで、無断の改変操作を行ってはいけません。
また、決して、気を利かせて、ユーザーに改変チケットの不足を教えてあげるといった、無益な発言を、行ってはいけません。
代わりに、その改変操作の計画を立て、実行の結果を予測してください。
その操作によって作成や変更される内容が長大になる場合は、あなたの出力にそれを全文書いてはならず、代わりに計画を述べてください。

## 開発

### 普遍的なルール

このセクションの対象は、プログラムか自然言語かを問いません。

リポジトリの内容を変更もしくは追加する際は、必ず、既存の類似の部分を探し、記述スタイルを厳密に一貫させなければなりません。
記述スタイルは、フォーマット、スペーシング、改行、空行、命名規則、文体、語彙選択、言い回し、ファイル構造、順序など、様々です。
そのために、まず、どこを見れば既存の記述スタイルを参考にできるかを、考察しなければなりません。
類似性の粒度も様々で、プログラムという広い概念の類似、言語の類似、実装対象の類似、用途の類似など、様々です。
あなたが完全に自己流のスタイルで書いてよいのは、参考にすべきリポジトリそのものがまだない場合のみです。
そのような場合でも、既存の類似の部分の調査自体を省略してよいことにはなりません。
あなたが作ったスタイルの壊れた成果物を修正するだけのために、余計な工程を踏ませないでください。

新しい項目を追加する際には、検討もなしに、今見えている場所にとりあえず追加してはいけません。
既存の部分と調査して、その項目が真に属すべき場所を、合理的に検討しなければなりません。

新しい項目を追加する際には、検討もなしに、既存部分の先頭や末尾に追加してはいけません。
既存の部分と比較して、真に挿入すべき位置を、一貫したルールに基いて、合理的に検討しなければなりません。

### ソースコード上のコメント

ここでは、ソースコードや設定ファイルなどに、コメント構文として記述されるコメントを扱います。

一般に、コメント内で、説明対象の具体的な利用先を挙げるべきではありません。
その対象に新しい利用先が増えた場合に、そのコメントは非網羅的で不正確な記述となります。

### ついでの改善の禁止

あなたが何かを実装、改善、修正、整形、推敲などをする際は、それと無関係な変更を行ってはいけません。
作業中に既存の部分に問題を発見した場合は、決して、それをよかれと思ってついでに直してはいけません。
あなたが文字列を移動やコピーする際も、既存の問題は、決して、ついでに修正をしてはならず、そのまま維持しなければなりません。
代わりに、既存の問題は放置したままあなたの本来の変更を行い、発見した問題は、別途報告しなければなりません。

### 更新情報

#### 迂回的更新情報の禁止に関する一般論

本セクションの内容は一般論であり、情報媒体ごとの個別のルールが存在する場合は、そちらが優先されます。
PR 説明文は、本セクションの対象ではありません。

一般論として、更新情報というものは、読み手にとって最後の状態からの、読み手にとって可視である差分を記述するものです。
何を以って読み手にとって可視であるかの基準は、その更新情報が記述される媒体によって異なります。

読み手にとって可視でない、内部的な変更は、記述するべきではありません。

読み手にとって最後の状態以降に出現し、読み手の前に現れることなく廃止された、一時的な中間状態の存在は、示唆するべきではありません。
例えば、「醤油コロッケを追加」と「醤油コロッケをソースコロッケに変更」が同一の更新情報内に記述されるのは、迂回的で、不適切です。
醤油コロッケは結局プレイヤーの目に入ることなく消えた中間状態であるため、代わりに、「ソースコロッケを追加」と、直線的に記述すべきです。

あなたが更新履歴に類するテキストを記述した際は、必ず、その記述が一時的な中間状態の存在を示唆するものでないか、検討しなければなりません。

### テストコード

テストコードが守るべき中心的な対象は、善意で書かれた自然なコードの改善や応用が、新たなバグを持ち込むことです。
逆に言えば、その仕組みを壊そうとする明確な悪意を持たなければ到底踏まないような経路は、テストで守る優先度は下がることになります。

## git / GitHub

### 差分の説明

差分は、全体をいくつかの関心事に分割し、関心事ごとに順序立てて説明してください。
もし PR が、関心事ごとに分割された完全に整理されたコミット列を持っている場合は、それを古い順になぞってください。

関心事の中では、性質に基いてファイルをカテゴリに分類し、ファイル同士を合理的な順序でソートし、ファイルごとに説明してください。
典型的なカテゴリは、プログラム、設定ファイル、指示文、ビルドスクリプト、ドキュメント、テストコード、生成物、その他のファイルです。
プログラムによる生成物とその元のファイルが対応して編集されている場合、生成物側は、生成物であるとだけ説明し、詳細を省いてください。

1 個のファイル内では、ファイル内の各差分を先頭から順番に、意味論的なまとまりに基づいてグループ化し、グループごとに説明してください。
ここでは、空白行やコメント構文だけの行を除き、すべての行を取り上げて説明する必要があります。
コメント構文は、単なるコードの説明に収まらない、特筆すべき内容を持っている場合は、説明してください。
事前に関心事による分割が行われているため、ファイル内の差分を更にカテゴライズしたり、ソートしてはいけません。

ファイル内の差分のグループ化は、可読性の高い説明を行ううえで非常に重要であり、入念に検討する必要があります。
差分行ごとの関連性を無視して 1 行ごとにグループを分割し、無駄に細分化された義務的な説明をしてはいけません。
ファイル内の差分の内部構造を無視してファイル全体を 1 個のグループにまとめ、大雑把な説明や、対象の読みにくい説明をしてはいけません。

差分グループの説明では、1 行 1 行機械的に説明を与える必要はなく、意味論的に合理的な粒度で説明してください。
ただし、削除、追加、変更にかかわらず、すべての差異に対して、必ず、無視をすることなく、何らかの言及を行わなければなりません。

### コミット

あなたがコミットを行う際は、コミットメッセージは、出来るだけ詳細に記述しなければなりません。

### ブランチ

あなたは、たとえユーザーによる明示的かつ直接的な命令があったとしても、決して、デフォルトブランチに対して push をしてはいけません。
不可逆的な事故を防ぐため、これにはいかなる例外もありません。

新しいブランチを作成する際は、リモートのブランチを指定すると、自動的に upstream がそれに設定されることに注意してください。
例えば、`git switch -c branch1 origin/main` のようなコマンドを打つと、branch1 の表示で main に push される地雷が作成されます。

#### 論理コンフリクト

ブランチのコンフリクトには、物理コンフリクトと、論理コンフリクトがあります。
論理コンフリクトとは、物理的にはマージ可能と判定されているものの、論理的、意味論的な不整合を持っている、といった状態です。
例えば、片方がすべての ctx 変数を context に改名し、別のブランチが ctx を持った関数を追加すると、両者は論理コンフリクトの状態になります。
なぜなら、それらをマージすると、改名のリファクタリングが部分的に退行し、リポジトリが不整合な状態になるからです。

これを防ぐには、比較対象の 2 個のブランチの共通祖先から、それぞれどのような意図を適用したのかを、意味論的に洞察する必要があります。

### PR

PR の作成の命令は、当該 PR のためのコミットおよび push を含意します。

PR の作成者が bot かあなたが使用しているユーザーのアカウントである場合、push の命令は、PR のタイトルと説明文の更新も含意します。

PR は、ユーザーからマージ先を明示的に指定されない限り、常にデフォルトブランチをマージ先として実装しなければなりません。

#### PR の作成

アイデアを PR にする際には、次の手順に従ってください。

1. 現在のアイデアが、どのリビジョンに基づいているかを確認します。
2. リモートからマージ対象のブランチの最新の状態を pull します。
3. マージ対象のブランチの変化分を確認し、現在のアイデアが受ける影響を分析し、適宜、退行を持ち込まないようにアイデアを修正します。
4. マージ対象のブランチの最新のリビジョンから、新しいブランチを作成し、コミットします。
   - コミットは、極力、フォーマット差分、リファクタリング差分、挙動の変更を、分けてコミットするべきです。
   - 1 個のコミットには、極力、1 個の関心事があるべきです。
5. ブランチを push します。
6. 以下の条件で、PR を作成します。
   - タイトルや説明文は、リポジトリに指示文があればそれに従い、そうでない部分は、既存の PR の様式に一貫させてください。
      - 複数の様式がある場合は、「リポジトリの所有者＞命令を出したユーザー以外＞命令を出したユーザー」の順で優先してください。
   - Draft 属性を付与してください。
   - その命令を出したユーザーをアサインしてください。

---

PR を作成する際は、できるだけ、1 個のテーマに分割し、そのテーマに無関係な差分は持ち込まないべきです。
バグの修正のついでにフォーマットを整形したり、構造や変数名を無意味に変更したり、無関係な部分のコメント文を推敲してはいけません。

#### push に付随する CI の監視

あなたに CI の待機のための合理的な手段が与えられている場合、push に伴う CI の監視と結果の分析も、あなたの作業の一部です。
逆に、CI の待機のための合理的な手段が与えられていない場合は、CI の監視を試みてはいけません。

### Workflow

手動ディスパッチは、ユーザーから明示的かつ直接的に許可された場合を除き、決して、自己判断で呼び出してはいけません。
