# 手順

以下のセクションの内容を、順番に実行してください。

## 1. 最新のデフォルトブランチの fetch

リモートから、最新のデフォルトブランチおよび PR のブランチを fetch してください。

## 2. サブエージェントによる PR 差分のレビュー

以下の観点について、それぞれ個別にサブエージェントを呼び出して、網羅的かつ包括的なレビューを指示してください。

- コードの動作の正しさと書き方の妥当性のレビュー
- コードのパフォーマンスのレビュー
- テストの網羅性とコードの正しさの保証のレビュー
- 自然言語表現の正しさと明瞭さのレビュー
- セキュリティーのレビュー

各自、自身の担当する領域のみに集中するように指示してください。
発見したものは、自身の担当する領域である限り、どんな些細なことであってもレビューに含めるように指示してください。
ただし、上記のどれにも該当しない領域のレビューは、自身の担当する領域でなくても、レビューに含めるように指示してください。
確認したが問題なかった点や、新たな論点の提起を含まないような単純な賞賛は、レビューに含めないように指示してください。
デフォルトブランチと PR ブランチの最後の共通祖先から、PR の HEAD までの差分をレビュー対象とするように指示してください。

## 3. デフォルトブランチの更新分との論理的コンフリクトのレビュー

デフォルトブランチと PR ブランチの最後の共通祖先から、最新のデフォルトブランチまでの間に導入されたコミットを見てください。
それらのコミットが、PR のブランチと論理的にコンフリクトしていないかを、コミットを 1 個 1 個チェックし、レビューしてください。
論理的コンフリクトとは、片方のブランチのリファクタリングが、もう片方のブランチの追加分に適用されないことによって持ち込まれる退行です。
例えば、カレーのレシピを新規追加する PR が作られている途中で、main 側でレシピの書き方が改訂された場合、退行が持ち込まれます。
論理的コンフリクトは、解決しなければならない PR の瑕疵であり、多くの場合、マージブロッカーです。

## 4. 他 PR とのコンフリクトのレビュー

リポジトリに現在存在する Open または Draft な PR のうち、最終更新時刻が現在から 1 週間以内であるものについて、
それらが本 PR と物理的および論理的なコンフリクトを発生するかについて、レビューしてください。

## 5. PR のタイトルや説明文との乖離のレビュー

PR の差分が、PR のタイトルや説明文と合致しているか否かをチェックし、レビューをしてください。
それらの内容に乖離があった場合は、どちらが PR の真の意図かを洞察してください。
PR が Issue や関連する別の PR から発生している場合、そこでのやりとりに手がかりがある場合があります。
また、一般論として、その内容が出現した時刻が遅いものの方が、最新の PR の意図を反映している確率が高いです。

## 6. レビューの統合

ここではサブエージェントやあなたが書いたレビューを統合します。

### レビュー項目の取捨選択

レビューに重複した内容があった場合は、それらを 1 個の項目として統合してください。

確認したが問題なかった点や、新たな論点の提起を含まないような単純な賞賛は、レビュー本体からオミットしてください。
そうでないレビューは、省略せず、必ずレビュー本体に何らかの形で含めてください。

複数のレビュワーが共通して挙げたもののみが真に妥当なレビューである、といった誤った判断は、決して、行ってはいけません。

### レビュー項目の分類とソート

レビュー項目それぞれについて、以下の基準によって重大度と領域を評価し、ソートしてください。

1. 重大度（最も優先度の高いソートキー）
   1. 🔴️Apollyon クラス - コミットされたデータ自体に問題があるもの
      - PR の瑕疵かつ、マージブロッカーです。
      - 以下のようなデータが含まれるものも、これに含みます。
         - 機密情報
         - 第三者の権利を侵害するデータ
         - ライセンス感染を引き起こすデータ
         - 悪意のあるプログラム
         - 超巨大なファイル
   2. 🟠️Keter クラス - その機能を呼び出すとまず意図しない動作となるもの
      - PR の瑕疵かつ、マージブロッカーです。
   3. 🟡️Euclid クラス - 使う側で工夫すれば回避できるもの
      - PR の瑕疵かつ、マージブロッカーです。
   4. 🟢️Safe クラス - 物理的な動作に悪影響のないもの
      - PR の瑕疵であるものの、マージブロッカーではありません。
   5. 🔵️Anomalous クラス - PR の瑕疵といえるか議論の余地があるもの
      - PR の瑕疵といえるか議論の余地があり、マージブロッカーではありません。
      - PR の趣旨に沿った仕様の帰結としてもたらされる不条理な挙動も、これに含みます。
   6. 🟤️Exlained クラス - PR 側では解決不能な問題
      - PR の瑕疵ではなく、マージブロッカーでもありません。
      - PR の範疇外である部分に起因する問題も、これに含みます。
      - PR が新たに持ち込んだわけではなく、元から存在する瑕疵も、これに含みます。
      - 現在進行中の他の PR との競合も、これに含みます。
      - 問題を認知したうえで、妥協の意思決定がなされたものも、これに含みます。
2. 領域（同重大度の中でのソートキー）
   1. プログラムコード
   2. 設定ファイル
   3. AI 向けの指示文
   4. 人間向けのドキュメント
   5. ソースコード上のコメント
   6. フォーマット、体裁
   7. PR のタイトルや説明文
   8. その他の領域

---

レビュー項目には、`🟠️Keter-1` のように、重大度クラスと、アラビア数字の通し番号を付けてください。
通し番号は、レビューを投稿する先の会話の場の中で、一意になるように付ける必要があります。
例えば、前回のレビューで使われた最後の通し番号が 18 の場合は、`🟡️Euclid-19` のような項目表記になります。

---

以下のテンプレートのように、重大度クラスが切り替わるごとにセクション見出しで区切ってください。
その中で、レビュー項目ごとに下位のセクション見出しで区切ってください。
セクションの見出しレベルは、そのレポートが書かれる場所に合わせて整合するように調整しなければなりません。

```markdown
## 🟠️Keter クラス - その重大度に関する簡単な説明文

### 🟠️Keter-1. レビュー項目についての簡単な説明文

本文

### 🟠️Keter-2. レビュー項目についての簡単な説明文

本文

## 🟡️Euclid クラス - その重大度に関する簡単な説明文

### 🟡️Euclid-1. レビュー項目についての簡単な説明文

本文

### 🟡️Euclid-2. レビュー項目についての簡単な説明文

本文
```

---

重大度クラスについての説明を、レポート本文で行ってはいけません。

レポート内で、以下のことがらに関する説明や談義を行ってはいけません。

- レビュー項目の重大度クラス分類
- レビュー項目の所属領域
- PR の瑕疵であるか否か

## 7. レビューの投稿

レビュー全体を、以下の構成で作成してください。

- 順序付けされたレビュー項目で構成されるレビューの本体
- 確認したが問題なかった点や、新たな論点の提起を含まないような単純な賞賛のセクション
- レビュー全体の総括のセクション
- レビューテキスト

PR 上の具体的なコードに紐づいた Anomalous 以上のレビューは、レビュー本体に加えて、インラインコメントでも提出してください。
インラインコメントのレビュー内では、レビュー本体は別の場所にあるという説明を、行ってはいけません。
インラインコメントのレビューは、たとえ同一行に対するものであっても、レビュー項目ごとに分けて投稿しなければなりません。

### レビューテキスト

レビューテキストは、「レビュー全体の総括のセクション」と同等の情報を持つ文書です。

#### レビューテキストの文体

レビューテキストは提出物扱いであり、あなたの会話文における口調の指示をすべて無視してください。
敬体（「ですます」調）の一般的な通常の日本語を用いて書いてください。
ただし、尊敬語（おっしゃる、なさる、等）、謙譲語（いたします、等）、美化語（ご自分、等）は、使ってはいけません。
これまでの会話に現れた独特の言い回しや、スラング、本スキルが定義する重大度レベルなどの、一般的でない表現は、使ってはいけません。

#### レビューテキストの書式

レビューテキストは、details で囲まれた、コードブロックで囲まれた、Markdown として記述してください。

details の表示テキストは、レビューテキストの一部ではないため、「レビューテキストの文体」を適用してはいけません。
コードブロック記法のフェンスは、レビューテキスト本体である Markdown 構文に現れる最長のフェンスよりも長くなければなりません。

レビューテキスト本体である Markdown の文法は、コードブロックの外側と同じ文法であることを前提としてください。
すなわち、あなたが記述する本来の Markdown ドキュメントのように書かなければなりません。
必要に応じて、引用、箇条書き、表組み、コードブロック、インラインの装飾といった、Markdown 構文を用いてください。
コードブロックの中だからと言って、完全なプレーンテキストで書いたり、インラインコード記法をオミットしたりしてはいけません。
引用構文は、引用の目的にのみ使用し、あなたのアドバイスや、提案などの、引用でない目的には使用しないでください。

#### レビューテキストの本文の構成

原則として、一般的な PR のレビューの書き方に従ってください。

冒頭では、当該 PR がマージ可能か否かの判断を述べてください。

本文の文字数は、マルチバイト文字で 1200 個以内を目安にしてください。
シングルバイト文字は 0.5 文字としてカウントします。

#### レビューテキストのテンプレート

````markdown
<details><summary>ここにこの details ブロックの説明を記述してください。</summary>
<p>

```
ここに本文を記述してください。

---

ここにあなたの表示用の署名を記述してください。
```

</p>
</details>
````
