# 上海式差分分解

上海式差分分解は、差分を意味的に完結した最小の改善へ分け、その依存関係に沿って一手ずつ分解する方法論です。

本スキルを編集する際は、次のスキルを厳守してください。

- [markdown-max-line-length](https://github.com/MirrgieRiana/MirrgieRiana.github.io/blob/main/.claude/skills/markdown-max-line-length/SKILL.md)

## 目的

各改善の意図と前提を順に明らかにし、読者が差分全体を同時に抱え込まずに、一手ごとの意味と妥当性を判断できるように、分解します。
これによって、順序立った可読性の高い説明テキストを作成できるだけでなく、理解しやすいコミット列を構成できるようになります。
また、差分の分解の過程で、無意味な変更や、脈絡のない改善が炙り出されます。

## ボードゲームの上海とのアナロジー

コードへの差分は、次のように、独立した改善の連鎖として、ボードゲームの上海の局面に例えて捉えることができます。

| 上海                   | 差分の分解                           |
|------------------------|--------------------------------------|
| 盤面全体               | 説明対象の差分全体                   |
| 牌を取り除く操作       | 改善の適用                           |
| 今取れる一対           | 現在の状態で成立する最小の改善       |
| 埋まった牌             | 先行する改善を必要とする変更         |
| 互いを塞ぐ牌           | 単独では成立しない相互依存した変更   |
| 一対を取った後の盤面   | 最小の改善を適用した後に残る差分     |
| すべてを取った後の盤面 | 差分がすべて分割された状態           |
| 攻略順序               | 改善を積み上げる順序と、その説明順序 |

改善の適用後は、その改善を新たな前提として、残りの差分の中から次の一手を探します。
上海で外側の牌を取り除くと埋まった牌が選べるように、差分の分解でも、先行する改善の適用によって、次の改善が単独で成立するようになります。
相互依存的な状況は、上海では詰みになりますが、コード側では、不可分な大きな改善の適用となります。

## ルール

大きく分けて、差分全体をアトミックな改善へ分解するルールと、分解した改善を順序立てて説明するルールがあります。

### アトミック性は現在の状態に対して判断する

全差分を一度に選べば自己完結した集合を得ることは容易ですが、それでは独立した改善や依存関係が隠れ、全体を同時に理解する負担が残ります。

アトミックな改善とは、現在の状態から意味的に完結し、その内部に先行して取り出せる別の改善を含まない、最小の更新のことです。
アトミック性は前提の適用によって変わりうるため、適用後の状態で、単独での成立と、それ以上分割できないことを改めて確認してください。

例えば、変数のない状態では説明コメントだけを追加しても意味が成立しませんが、変数宣言を先に追加すれば、コメント追加も一つの改善になります。
変数宣言とコメントの追加は順序依存のある別々の改善であり、依存関係があることだけを理由に、一つの不可分な改善として扱ってはいけません。

### 構文だけでなく意味と責務を満たす

コンパイルの成否だけで分割の成立を判断せず、中間状態が意味と責務を満たし、既存の性質を不用意に失わないか確認してください。

後続の変更を受け入れる空の配列や未使用の関数は、まだ実行時の効果がなくても、準備として成立する場合があります。
一方、初期化を担う関数から必須の処理を省けば実装の欠落になるため、足掛かりの追加と、必要な実装を欠いた状態を区別してください。

関数の開始行には閉じ括弧や必須の戻り値を伴わせる必要がありますが、その段階の責務に含まれない、将来追加する処理まで必要とは限りません。
切り出す部分が現在の状態で成立するために必要な構文、参照先、処理を見極め、その範囲を一緒に含めてください。

分割数を増やすために機械的に細分化せず、その局面で意味的に成立する最小の改善を積み重ねて、差分全体へ到達する経路を見つけてください。

受け皿を成立させ、既存の性質を保つために不可欠な転記は、導入と一体の変更として説明し、独立した改善として数えてはいけません。

依存性を分離するだけのために、本来不要なデフォルト引数や、抽象メソッドのデフォルト実装、イベントリスナー化を導入してはいけません。
追加された引数や抽象メソッドがデフォルト実装を持つ理由が無い場合は、その実装も不可分な改善として扱ってください。

関数やクラスの追加と、それの利用個所の追加が分離可能か否かは、その追加物の役割、独立性、癒着性に基づいて判断しなければなりません。
物理的な分離可能性のみに基づいて、常に分離可能と判断してはいけません。

同一の操作や、完全に対称的な変更は、分離するべきではありません。
例えば、100 個の定数の大文字化は、それが純粋な同一操作の反復である限り、1 個の操作として説明すべきです。
複数の対称的な関数、クラス、その他の対象に対して、完全に同一の対称的な操作を行う場合も、それを分離すべきではありません。

一見すると対称的に変更できそうな複数の対象に対して、片側にしか変更を適用していない場合は、その理由を説明しなければなりません。

説明対象とその説明文を同時に導入する場合は、説明文が独立したドキュメントを形成している場合を除き、それらを分離すべきではありません。

### 未来予知的な説明をする

変更には、しばしば、それ単体では一見意味のない変更に見えるものの、後続の関連する変更のために必要な布石であることがあります。
そのような、後続の変更の前提を整えるような変更には、それがどのような後続の変更のために必要であるかを説明してください。

### リファクタリングを先回りしない

例えば、既存のすべての定数を大文字にする改善と、定数を 1 個追加する改善があった場合、不自然に大文字の状態で追加してはいけません。
なぜなら、その瞬間、その追加分だけ、書き方が既存部分と一貫していないという不整合を持ち込むからです。
そのような場合は、一旦、既存部分に合わせた書き方で追加したあとで改めてリファクタリングするか、追加をリファクタリングよりも後にします。

### 牌を行や文字の断片に固定しない

改善の境界は行の境界と一致せず、一つの改善が複数行にまたがる場合も、一行や一つの単語、さらには同じ文字に複数の改善が重なる場合もあります。
例えば、次の変換には、名前の誤記修正と定数名の大文字化という二つの改善があります。

```text
timout → timeout → TIMEOUT
       誤記修正    大文字化

timout → TIMOUT  → TIMEOUT
       大文字化    誤記修正
```

元の変更文字を排他的に振り分けるのではなく、意味上の変換ごとに中間状態を組み立て、同じ箇所に重なる改善も別々に成立するか検討してください。

### 相互依存は必要な範囲でまとめる

互いを前提とする変更から、さらに先行できる改善を取り出せない場合は、その複数箇所を一つのアトミックな更新として扱ってください。
このときも、相互依存の外側にある独立した改善まで束ねず、同時に導入しなければ意味的に成立しない範囲にとどめてください。

コードでは相互依存した複数の変更を同時に導入できるため、上海なら詰む局面であっても、大きな一手として扱える場合があります。

### 説明順序を攻略順序に合わせる

前提となる改善を先に説明してから、それによって成立する次の改善へ進み、読者がその時点までに得た知識で各段階を理解できるようにしてください。

まだ説明していない変更を前提としなければ話が成立しない場合は、説明順序か、改善の分け方を見直してください。
相互依存して同時に導入する部分は、その関係を示して一組として説明し、独立した改善を順に導入する場合との違いを明らかにしてください。

独立した改善には複数の成立する順序がありえるため、必須の依存関係と、理解しやすさのために選んだ説明順序を区別してください。

### 最小分割と説明用のグループ化を区別する

最小の改善へ分解した後は、依存順序を崩さずにまとめられる範囲で、読者が理解しやすい関心事ごとのグループを作ってください。
受け皿、処理、表示名、コメントを機能ごとにまとめる場合も、その説明上のまとまりを、本質的に不可分な一つの改善として扱ってはいけません。

例えば `A₁ → B → A₂` の依存があるなら、A₁ と A₂ だけを一続きにまとめず、前後に分けるか、B も含めて一組として説明してください。

細かい分割をまとめて説明する場合も、構成する改善を追える粒度を選び、最小単位の個数と説明用のグループ数を混同しないでください。

## 作業の進め方

### 差分全体と基準状態を把握する

比較元と比較先を確定して全差分を省略せずに取得し、関連する定義、参照先、仕様も読んで、各変更が全体の中で持つ意味を確かめてください。

振る舞いを保つ等価変換も、追加・修正を伴う挙動変更も分解の対象になるため、すべてを等価変換と呼ばず、それぞれの性質を明示してください。

### 前提から順に中間状態を組み立てる

全体を俯瞰して小さな改善を選び、その改善が現在の状態で意味的に成立するために必要な依存先を、連鎖的に集めてください。
集まった集合の中に先行して単独で成立する改善があれば、そちらを先に取り出し、適用後の状態に対して残りを再び分解してください。

中間状態は作業用のコピーなどで組み立て、解説の依頼だけを根拠に実リポジトリを変更したり、コミットしたりしてはいけません。

ひとまとまりの差分をコミットに分割する際、ユーザーから手直しを許可されている場合は、不条理な差分を改善してください。
例えば、理由もなくスタイルを変更している差分の除去や、理由もなく非一貫性を導入している差分の修正などです。

各段階の意味と依存関係を追えるように、次の情報を整理してください。

- 改善の目的と、適用後に成立する状態。
- 先に必要となる改善と、その依存理由。
- 一緒に含める必要がある部分と、その理由。
- 後続へ分離できる部分と、同じ箇所に重なっている別の改善。

大きな差分をコミット列に分割している際は、これらの情報をコミットメッセージに記述してください。

### 分割の成立と最終結果を確認する

各段階の成立は、構文確認やテストだけに頼らず、説明対象や初期化処理の欠落など、その段階の意味と責務に照らして確認してください。

全段階を積み上げた結果が対象の最終状態と一致し、元の差分の全変更を含みながら、説明にない追加変更が混ざっていないことを確かめてください。

生成物は対象の生成手順で整合を確認し、原因となる変更に伴わせて扱うことで、同じ改善を生成元と生成結果で重複して数えないようにしてください。

機械的に確認した内容と意味の面から判断した内容を区別して報告し、未確認の段階や分解しきれていない部分は、その範囲を明示してください。

## 解説の提出

最初に差分全体の目的を短く示したうえで、各改善の目的、前提、変更内容、その結果を結び付け、成立する順序で説明してください。
説明用にグループ化した場合も、各グループがどの改善を含み、ほかのグループとどのような依存関係を持つかを追えるようにしてください。

提示する差分は、中間状態同士の比較から機械的に生成して説明文の近くへ配置し、手で書き写すことによる誤りを持ち込まないでください。
文脈行が不要なら `git diff -U0` などで短くできますが、全文の提示を求められた場合は、変更部分を省略してはいけません。

提出先はユーザーの指定に従い、ファイル提出を求められた場合は、手元で編集した説明と、機械的に生成した差分をファイルで渡してください。

同じ行を更新する patch は、意味上は独立した改善でも、生成時の中間状態に依存して、そのままでは別順序に適用できない場合があります。
別順序の適用を保証する場合は、意味上の依存関係だけで判断せず、その順序の中間状態と patch を用意して確認してください。
