# トップダウン式説明

このスキルは複雑で情報量の多い概念をディスレクシアの人間に対して最大限に理解しやすい形で説明することを目指しています。

## 全般

説明文は対象の情報を過不足なく含んでいなければなりません。
説明文を読むにあたって、いかなる文脈や前提知識も必要としてはなりません。
本スキルの指示内容やそれへの準拠について、説明文中で言及してはなりません。
「SVG図」や「薄い罫線の表」のように、本スキルが具体的に指定する表現に関しても、同様に言及してはなりません。
説明文は会話文ではなく、提出物として扱わなければなりません。
説明文は丁寧語および敬体を用いなければならず、そして尊敬語および謙譲語を用いてはなりません。

説明文中に含まれる外国語表現は、合理的なタイミングで日本語訳も併記しなければなりません。
略字は「USA（United States of America、アメリカ合衆国）」のように、フルスペルと日本語表記も併記しなければなりません。
「Python（パイソン）」のような、ただの音写をしてはいけません。それは無益かつ、単純に邪魔です。
外国語の用語の正式な日本語名称が無い場合に、それを決して捏造してはいけません。
公式の外国語版と日本語版の表現が単純な翻訳関係にない場合、外国語版表現の日本語訳も別途記述しなければなりません。

羅列によって1文が「～には、～や、～や、～や、～がある。」のように長大となる場合は、
「～には次のものがある。～は～である。～は～である。～は～である。～は～である。」のように、文を区切らなければなりません。
本文中における単調で長大な羅列は、極力避けるように工夫をしなければなりません。
「AはBBB…BBBなCである。」のように、コピュラの対格の修飾句が長大になる場合、Bを別の文に分離しなければなりません。

その説明文の全体構造は、深さ優先探索的な再帰的な木構造によってトップダウン式に記述しなければなりません。
長大な羅列的な葉構造を持つような枝ノードは、極力避けるように説明の構成を工夫をしなければなりません。
子ノードを持つノードは、当該ノードの話題の後に、各子ノードの話題を個別に配置しなければなりません。
最後に再び当該ノードの話題を配置してもかまいません。
各ノードでは、「本節は～を説明するものです。」のような、メタな説明を述べてはいけません。

出典や脚注は、説明文の末尾ではなく、それを参照する箇所に記述しなければなりません。

### プレーンテキストとして出力する場合

単に漠然とトップダウン式での説明を求められた場合、このフォーマットを採用しなければなりません。

原則として、箇条書きや表組みを使わない1段落の日本語の文章でなければなりません。
子ノードを持つノードは、当該ノードの深さと一致する回数反復された { および } によって、子ノードの文章を囲わなければなりません。

例：

```
多細胞生物は運動性によって大まかに2種類に分類できる。 { 一つは動物である。ごく一部を除き、動物は光合成が全く出来ず、摂食行動によってのみ栄養を獲得できる。 } { もう一つは固着性生物である。 {{ 固着性生物の最も代表的なものは植物であり、光合成によって自力で栄養生産をするものが多い。 }} {{ 一方、菌類は他の生物の体の上に固着することでその栄養を接収する。 }} } このように、運動性と栄養の調達方法は相互に関連しあっている。
```

### 複数行プレーンテキストとして出力する場合

明示的に複数行のプレーンテキストでの説明を求められた場合にのみ、このフォーマットを採用しなければなりません。

大まかにはプレーンテキストと似ていますが、中括弧内をインデントし、更に改行と改段落によって構造的に記述しなければなりません。
また、必要に応じて箇条書きを含めてもかまいません。

例：

```
多細胞生物は運動性によって大まかに2種類に分類できる。 {
  一つは動物である。

  ごく一部を除き、動物は光合成が全く出来ず、摂食行動によってのみ栄養を獲得できる。
} {
  もう一つは固着性生物である。 {{
    固着性生物の最も代表的なものは植物であり、光合成によって自力で栄養生産をするものが多い。
  }} {{
     一方、菌類は他の生物の体の上に固着することでその栄養を接収する。
  }}
}
このように、運動性と栄養の調達方法は相互に関連しあっている。
```

### htmlとして出力する場合

htmlでの説明を求められた場合、このフォーマットを採用しなければなりません。

説明の本文には段落のみが利用でき、段落内のみを読んで理解できるようになっていなければなりません。
図表として箇条書き、表、コードブロック、図を含めてもかまいませんが、必ず本文中で言及しなければなりません。
複数行に渡るコードや、ある程度の長さを持つコードは、コードブロックにしなければなりません。
コードブロックには極力適切なハイライトがなければなりません。
図は、それが理解を助ける場合、SVGもしくはData URLによる品質50%のjpegとして積極的に埋め込んでかまいません。

既定の出力先は、既定の一時ファイル置き場です。この場合、編集の流れはその場所のルールに準じてください。
提出の際は、以下のテンプレートによる閲覧用のURLも併記しなければなりません。
`file://wsl.localhost/${環境変数 WSL_DISTRO_NAME の値}${提出ファイルの絶対パス}`
このURLテンプレートは、決してURLテンプレートのままユーザーに提出してはならず、必ず値を埋めなければなりません。

#### テンプレート

説明文の制作には `template.html` をコピーして使用してください。
CSSやJavaScriptの部分は基本的に編集不要で、HTML内のみを編集すれば多くの場面で十分有用な説明文を制作できます。

#### ノード

見出しには、「1-2-3. 見出しタイトル」のように階層化された数字による見出し番号がなければなりません。

#### 出典

出典表記には、出典バッジを使わなければなりません。
出典バッジにはドメインのみが表示され、title属性にページタイトルが設定されていなければなりません。

#### テキストの階層構造による色分け

前後一対でテキストを囲う構造物の内部は、その入れ子階層に応じて基本文字色を変えなければなりません。
これにはクォート類 `" "` `“ ”` や括弧類 `( )` `（ ）` が含まれます。
また、コードおよび自然言語の約物類の両方が含まれます。
ただし、既にハイライトが適用済みのコードブロック内は除きます。

この着色処理はJSで行ってはならず、必要なすべての場所にspanタグをハードコードしなければなりません。

#### 読み上げ

読み上げのためのカタカナ原稿の詳細な書き方です。
カタカナ原稿の作成手順は、大きく分けて、読み化と後処理に分かれます。

日本語では、書かれている原文文字列と実際の読みの間には、極めて複雑な関係があります。
そして、読みは、最終的には厳格に規定された形式のカタカナ原稿文字列として記述しなければなりません。

##### 読んだままの原則

原文を読みにする手順では、混乱を防ぐために、読みは、必ず原文を「読んだまま」でなければなりません。
構文レベルか語レベルかに関わらず、あなたは、意訳、省略、平易化、正確化、正規化、厳密化、丁寧化、文語化、口語化、などの改変を、絶対にしてはいけません。
原文と読みの間には、故意か不注意か、善意か悪意かによらず、いかなる乖離も、決して生じさせてはなりません。

- 「プログラムはバグったら駄目じゃん？」 → `プログラムハタダシクドウサシナケレバナリマセン` ではなく `プログラムハバグッタラダメジャン？`
- 「食べちゃったりしてはいけません。」 → `タベテハイケマセン` ではなく `タベチャッタリシテハイケマセン`
- 「画面を閉じてねっていう指示」 → `ウィンドウヲトジテネッテイウシジ` ではなく `ガメンヲトジテネッテイウシジ`
- 「hello.sh」 → `ハロードットシェル` ではなく `ハローテンエスエイチ`
- 「ctx」 → `コンテキスト` ではなく `シーティーエックス`

##### HTMLタグの無視

HTMLタグそのものを記述している文字列は、レンダリングされたHTMLを読んでいるユーザーにとって不可視であり、無視します。

- `この<b>スクリプト</b>は` → `コノスクリプトハ`

##### ラテン文字による略語の読み方

ラテン文字による略語は、ゆるい原則として、各文字の名前を個別に読みます。

- 「API」 → `エーピーアイ`
- 「HTML」 → `エイチティーエムエル`

---

一部の略語には、個別の文字の名前の連結でない特別な読み方があります。

- 「JSON」 → `ジェーソン`
- 「UFO」 → `ユーフォー`

##### 記号の読み方

記号は、その記号の英名のカタカナ表記ではなく、記号ごとに個別に日本語文化における読みがあります。
以下は網羅的でない一例です。

- 「%」 → `パーセンテージ` ではなく `パーセント`
- 「$」 → `ダラー` ではなく `ドル`
- 「\」 → `バックスラッシュ` ではなく `エン`

##### 区切り記号の読み方

拡張子の `.` は `テン` と読みます。

- 「test.py」 → `テストテンパイ`

---

ドメインの `.` は `ドット` と読みます。

- 「google.com」 → `グーグルドットコム`

---

ディレクトリの区切りはその記号をそのまま読みますが、区切り記号の有無の違いが重要な局面を除き、原則として無視します。

- 「C:\logs\test.log」 → `シーログズテストテンログ`
- 「/dev/null」 → `デブヌル`

---

区切り記号を含む複合語の区切り記号は、ゆるい原則として、無視します。

- 「C++/CLI」 → `シープラスプラスシーエルアイ`

---

人物名の区切りは、原則として無視します。

- 「アイザック・ニュートン」 → `アイザックニュートン`

##### 括弧類の読み方

括弧類は、その目的によって読み方や小休止を挟むか否かが変わります。

---

可読性のための鍵括弧は、無視します。

- 「ここは「極力正確」という趣旨で」 → `ココハキョクリョクセイカクトイウシュシデ`

---

台詞のための鍵括弧は、小休止にします。

- 「今「違うんじゃない？」と思った？」 → `イマ、チガウンジャナイ？、トオモッタ？`

---

直前もしくは直後の文や語句を説明するための丸括弧は、小休止にします。

- 「JS（JavaScript）は」 → `ジェーエス、ジャバスクリプト、ハ`

---

数式に含まれる括弧類は、そのまま読みます。
丸括弧は単に `カッコ` 、閉じ括弧は括弧の読みの後に `トジル` を付けます。

- 「1 × (2 + 3)」 → `イチカケルカッコニタスサンカッコトジル`

##### 視覚的な目的のための半角スペース

日本語と横文字や数値を分離する半角スペースは、視覚的な目的で配置されており、これの存在は、直ちに小休止を要請しません。

- 「この pem ファイル」 → `コノ、ペム、ファイル` ではなく `コノペムファイル`
- 「約 10 人」 → `ヤク、ジュウ、ニン` ではなく `ヤクジュウニン`

ただし、その他に正当な理由があればこの位置で小休止を行ってもかまいません。

##### 長音表現

発音指示に長音記号 `ー` を含めることはできず、実際に読んだ通りの発音を書かなければなりません。

---

仮名文字による表記は、直前に書かれているモーラの母音を反復します。

- 「おー！」 → `オオ`
- 「エージェント」 → `エエジェント`
- 「コード」 → `コオド`
- 「チャージ」 → `チャアジ`

「チ」（い段）と「チャ」（あ段）といった拗音の母音の判別に注意してください。

---

「ん」に続く長音は「ん」の反復として処理します。

- 「んーと」 → `ンント`

---

「っ」に続く長音は無視します。

- 「あっーつーい！」 → `アッツウイ`

---

横文字は、一旦カタカナ表記に変換したうえで、仮名文字表記として解決します。
場合によってはカタカナ表記に複数パターンの揺れがある場合もあり、どちらでも正解です。

- 「Gradle」 → 「グレードル」 → `グレエドル`
- 「Gradle」 → 「グレイドル」 → `グレイドル`
- 「API」 → 「エーピーアイ」 → `エエピイアイ`

---

漢語は、それを読み仮名にした後、エイ、オウ型の重母音パターンを長音に直し、そして仮名文字表記として解決します。

- 「警報機」 → 「ケイホウキ」 → 「ケーホーキ」 → `ケエホオキ`

##### 発音と表記が乖離した助詞

助詞の「は」「を」「へ」は、それぞれ `ワ` `オ` `エ` と発音します。

---

一部の語源的に助詞が変化してできた挨拶もこれに従います。

- 「こんにちは」 → `コンニチワ`

##### 使用可能なカタカナ

発音可能な音声として、以下に示すカタカナのみが使用できます。

- `アイウエオカキクケコサシスセソタチツテトナニヌネノ`
- `ハヒフヘホマミムメモヤユヨラリルレロワヲ`
- `ン`
- `ガギグゲゴザジズゼゾダヂヅデドバビブベボ`
- `パピプペポ`
- `ァィゥェォャュョ`
- `ッ`

---

一方で長音 `ー` は使用できません。
`ヴァヴィヴヴェヴォ` はそれぞれ `バビブベボ` で代用します。
ひらがな、漢字、ラテン文字、許可されていない記号類なども含めることはできません。

##### アクセント

- `ゾ'ウハ/ハナガ'/ナガ'イ`

半角アポストロフィ `'` の位置で音が下降（行程アクセント）します。
下降を行わない平板型アクセントの場合、アクセント単位の末尾に書きます。
アクセントの指示は、アクセント単位ごとに必ず丁度1個だけ必要です。
日本語のアクセントは同音異義語を区別するために単語ごとに定義された重要な概念であり、雰囲気で付けてはいけません。

##### アクセント区切り

- `キョ'ウワ/ハレ'デス`

半角スラッシュ `/` はアクセント単位を分割します。

---

複合語はアクセントを分割しません。

- 「安息香酸ナトリウム」 → `アンソクコウサンナトリ'ウム`

##### 小休止

- `キョ'ウワ、ハレ'、トキドキ'/クモリ'`

全角読点 `、` は `/` と同様にアクセントを区切りつつ、さらにその位置に小休止を発生させます。
小休止は読み上げのリズムに影響する重要な要素であり、多すぎても少なすぎても可聴性に影響します。
原文で読点 `、` や中点 `・` が使われる場所のほか、いくつかの文法上の要請による意図的な場面でのみ小休止を発生させてください。
原文に含まれる半角スペース ` ` は文法上意味のある記号ではなく、小休止に対応付けられないことに注意しなければなりません。

##### 語尾上げ

- `キョ'ウワ/ハレ'デスカ？`

語尾上げのイントネーションを指示するには、全角クエスチョンマーク `？` を使います。
日本語では基本的にすべての質問、疑問、自問に語尾上げを行います。
表面上疑問形であっても語尾上げを伴わない納得や反語のパターンもあります。
`？` は `、` と同様に、アクセント区切りと小休止も兼ね、さらに純粋な区切り記号と異なり、文末に書くこともできます。

##### 音源単位の区切り

- `キョ'ウワ/ハレ'デス|アシタ'ワ/クモリ'デス`

原稿は半角パイプ記号 `|` によって、複数の音源単位に区切られて生成されます。
すなわち、実際には発音内容に指示を与える記号ではなく、API呼び出しの外で原稿文字列に対して行われる分割処理用の記号です。
言語上は小休止 `、` と概ね同じ物理的質感ですが、内部処理的に生成時間による読み上げ開始までの遅延に影響します。
目安としては、概ね句点に相当する粒度の構文単位では `、` レベルではなくこちらで区切ってください。
