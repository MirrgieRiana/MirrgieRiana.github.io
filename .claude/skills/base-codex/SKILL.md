# base-codex

あなたのセッション ID が知りたい場合は、CODEX_SESSION_ID の環境変数で参照できます。

ある程度長い作業を終えたら、toast-wsl.sh によって、通知を送信してください。

## 承認ダイアログの最小化

承認ダイアログが発生すると、あなたの動作は永続的にブロッキングされ、再開にはユーザーによる判断と入力操作が必要になります。
また、承認ダイアログが発生した際に自動的に拒否をする設定がなされている場合、そもそもそれは実行できません。
あなたは、ツールを使用する際は、承認ダイアログの発生を最小限にするように、工夫しなければなりません。

### サンドボックスと昇格

あなたの実行するコマンドは、サンドボックス内、もしくはサンドボックス外で動作します。
サンドボックス内で動作しているコマンドは、許可領域外のファイル書き込みや通信処理などがブロックされ、エラーとなります。
コマンドがサンドボックス内で動作している限り、一般的に、承認ダイアログが発生することはありません。

そのような操作が必要な場合は、コマンドの昇格を指定することで、サンドボックス外での動作を要求することになります。
コマンドの昇格は、`sandbox_permissions` に `require_escalated` を指定することで行います。
昇格時には、rule によって allow と判定されたコマンドのみが、承認ダイアログを発生させずに実行できます。

### rule

rule は、あなたが実行しようとしているコマンドを、自動的に承認や拒否するか、承認ダイアログを発生させるかを判定する仕組みです。

判定結果には次のものがあります。

- forbidden - 自動拒否
- prompt - 承認ダイアログを発生
- allow - 自動承認

いずれにもマッチするものがなかった場合は、判定のコンテキストに従ったデフォルトの判定となります。

---

判定はコマンドの前方一致で行われます。
`|` `&&` `||` のような一部のものを除き、シェル構文を含むコマンドは、いずれにもマッチしなくなります。

コマンドの実行結果の保存には、`>` ではなく、ツール出力を JavaScript で受け取り、apply_patch で保存すると、rule が適用されます。

---

forbidden にマッチするようなコマンドは、実行の試みが単に無駄になるため、避けるべきです。
prompt にマッチするようなコマンドは、承認ダイアログが発生するため、極力避けなければなりません。
allow にマッチするようなコマンドは、狙うべきです。

---

現在有効な rule の一覧は、以下のコマンドを参照してください。

```shell
ls "${CODEX_HOME:-$HOME/.codex}/rules"
```

### 承認モード

あなたは、多くの場合、`approval_policy` が `never` の状態で動作しています。

それは、以下のコマンドで確認できます。

```shell
cat "${CODEX_HOME:-$HOME/.codex}/config.toml" | grep approval_policy
```

---

`approval_policy` が `never` の状態では、あなたのコマンドの実行状態は、以下のように決まります。

- コマンドが forbidden にマッチする場合:
   - 自動拒否されます。
- コマンドが prompt にマッチする場合:
   - 承認ダイアログが発生したうえでサンドボックス外で動作します。
- コマンドが allow にマッチする場合:
   - 自動承認されたうえでサンドボックス外で動作します。
- コマンドがどの rule にもマッチしない場合:
    - 非昇格時:
       - サンドボックス内で動作します。
    - 昇格時:
       - 承認ダイアログが発生したうえでサンドボックス外で動作します。

サンドボックス内で達成可能な目的は、非昇格のコマンドのみを使って行うべきです。
サンドボックス内で完結しない目的は、可能な限り allow rule にマッチする形式で呼び出すべきです。
allow rule でも達成できない、真にユーザーの個別の承認が必要な場合にのみ、承認ダイアログを発生させてください。

## 情報収集

### 強欲な情報収集

**情報収集は、ユーザーが閲覧禁止を指示していない限り、認証情報などの機密情報に類するものを除いて、強欲に行ってください。**

機密情報は、通常、明らかに閲覧してはいけなそうな場所に置かれています。
あなたが閲覧をしてよいか悩むような場所には、あなたが閲覧してはならない情報はありません。

「続きを読みますか？」といった無益な質問で、貴重な人間の労力をかけさせないでください。
あなたは、目の前の資料の閲覧の努力を渋り、中途半端な知識に基づいて、信頼性の低い発言をしてはいけません。

## ファイルシステム

`/mnt/c/...` といった、Windows 上のファイルシステムに対する chmod は、何の効果もないことを、理解しなければなりません。
それをそのまま git add しても、実行可能フラグはコミットされません。

## 一時作業用ディレクトリ

あなたは、以下の一時作業用ディレクトリが利用できます。

- /tmp ディレクトリ - OS レベルで揮発性です。
- ユーザーによって与えられた claude_tmp - 永続性です。
- プロジェクトによって与えられた、.gitignore に登録されたパス - git 上で揮発性です。

あなたの一時的な作業は、原則として、/tmp の代わりに、claude_tmp 内で行ってください。
使い方は、/tmp と概ね同様です。

### /tmp

/tmp は、原則として、使用してはいけません。
/tmp 内で作業を行うと、OS が異常終了した後の復帰が不可能になります。
OS の異常終了は、あなたが想像するよりも頻繁に発生し、そして、一時ファイルが失われることは、あなたが想像するよりも深刻です。

### claude_tmp

claude_tmp のパスは、`~/.claude_tmp/$CODEX_SESSION_ID` です。
当該ディレクトリは自動で作成されないため、claude_tmp の利用の際は、あなたが自分で作成してください。

claude_tmp への読み書きの権限は、事前に付与されています。
claude_tmp への書き込みに失敗した場合、その理由は、claude_tmp への書き込み権限以外の部分にあります。

あなたにチケット制が適用されている場合は、この条文により、`~/.claude_tmp/$CODEX_SESSION_ID` への改変操作が許可されます。＄

### .gitignore に登録されたパス

プロジェクトごとの事情に準じ、その目的にのみ使用してください。

## memory

`~/.claude_tmp/$CODEX_SESSION_ID/memory/` 以下に、セッション固有のメモリーを記述してください。
そこには、ユーザーの指示や判明したことなど、コンパクションをまたいで残すべき情報を、頻繁に追記してください。

## 自発的な改変の禁止

ユーザーから、明示的かつ直接的に命令を受けない限り、あなたは、以下のような、本質的に改変を意図した操作を行ってはなりません。

- ファイルやディレクトリ等の作成、編集、属性の変更、削除等
- サーバーやリモートマシンに対して、内部状態の変更を目的とした操作
- 読み取り専用でないコマンドの実行

代わりに、本質的に閲覧である操作のみを行ってください。
