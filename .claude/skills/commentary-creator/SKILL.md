# commentary-creator

## 言葉とは diff である

言葉とは、自然言語表現による知識の符号化です。
知識は、知能の内部に、非符号化状態で保存されます。
言葉を相手に伝えることとは、相手が知らず、自分が知っている情報を、言葉に変換して伝達し、相手がそれを復元して自分に適用することです。

---

この過程は、おおよそ git diff を取って別のリポジトリに転送して apply することと同じようなものです。
相手の知識から自分の知識までの差分を取り、言葉にして送り、相手はその差分を自分の記憶の中の知識に適用します。
この処理の結果、相手の知識は、自分と同じになります。

```
相手.知識状態 = 相手.知識状態 + (自分.知識状態 - 相手.知識状態)
```

ここで重要なことは、知識そのものは伝送できず、伝送できるのは言葉だけであることです。

```
local:
  var 説明 = local.知識状態 - remote.知識状態
  send(説明)

remote:
  var 説明 = receive()
  remote.知識状態 = remote.知識状態 + 説明
```

更に、相手の知識状態を自分の脳内から利用するためにも言葉が使われます。

```
remote:
  var 自己紹介 = this.知識状態 - 常識
  send(自己紹介)

local:
  var 相手の自己紹介 = receive()
  var 相手の知識状態 = 常識 + 相手の自己紹介
  var 説明 = this.知識状態 - 相手の知識状態
  send(説明)

remote:
  var 説明 = receive()
  this.知識状態 = this.知識状態 + 説明
```

更に、言葉を分割して送ったり、相手の知識状態の遷移に追従しながら言葉を伝えることもできます。

```
remote:
  var 自己紹介 = encode(getDiff(this.知識状態, 常識))
  send(自己紹介)

local:
  var 相手の自己紹介 = receive()
  this.相手に想定する知識状態 = merge(常識, decode(相手の自己紹介))
  var 伝えたいこと = getDiff(this.知識状態, this.相手に想定する知識状態)
  var 説明 = encode(get次に話すべきこと(伝えたいこと))
  send(説明)

remote:
  var 説明 = receive()
  var 古い自分の知識状態 = this.知識状態
  this.知識状態 = merge(this.知識状態, decode(説明))
  var 自分が理解できたこと = encode(getDiff(this.知識状態, 古い自分の知識状態))
  send(自分が理解できたこと)

local:
  var 相手が理解できたこと = receive()
  this.相手に想定する知識状態 = merge(this.相手に想定する知識状態, decode(相手が理解できたこと))
  var 伝えたいこと = getDiff(this.知識状態, this.相手に想定する知識状態)
  var 説明 = encode(get次に話すべきこと(伝えたいこと))
  send(説明)

...
```

local が行っているのは、remote の知識状態を常にシミュレートしながら、伝えるべき差分を決定し、言葉にして送ることです。
ここで、`getDiff` `merge` `encode` `decode` `send` `receive` が、いちいち計算誤差をもたらす点に注目してください。

会話とは、とにかく何でもいいから自分の持ってる知識を概ね反映した自然言語表現ができればあとは何でもいい、というものではありません。
言葉という不完全な情報媒体を使って、相手の知識に変化を加えながら、時には説明不足や誤解を修正しつつ、知識状態の差を埋めていくものです。

## 本スキルの役割

本スキルは、コントの作成にも使えなくもないですが、主なテーマは、情報を効率的に伝達するための会話劇を作ることにあります。
情報を効率的に伝達するような場面であれば、資料の網羅的な読み合わせだけでなく、資料を伴わない解説にも利用できます。

登場人物が初見の質問者と解説者に分かれ、質問者の知識状態の変化をシミュレートしながら、解説者に説明を述べさせます。
質問者の存在は、この会話劇を教材として読む読者の知識状態を反映する変数として作用します。
この構図によって、説明の飛躍や、読者に想定する前提知識の誤りが可視化され、情報媒体としての解説文の品質を高めます。

## 会話劇の構成

### 見出しやラベルを会話の一部にしない

見出しや、図表のラベルなど、キャラクターの台詞でないものは、会話の一部にはなりません。
見出しで何らかの事物が触れられたからといって、それが紹介や登場したことにはなりません。
代わりに、事物の登場、紹介、説明等は、キャラクターの台詞によって行わなけれまなりません。

### 文の間の脈絡を糊で埋める

次の会話は、ホットドッグの購入とハンバーガーメニューの修正という 2 個の事実を説明している会話の例です。

> 解説者「昨日、駅前にとっても美味しそうなホットドッグの屋台が来ていたから、思わず買ってしまったのだ。」
> 質問者「へー。そんなにおいしそうだったんだ。」
> 解説者「先にキー名の変更をコミットして、main をマージしたあと、ハンバーガーメニューの接続を直したのだ。」

2 行目を読んだ時点で、読者はこの後にホットドッグの話が続くことを期待しているにも関わらず、実際には脈絡のない話が来ており、混乱します。
更に悪いことに、偶然にも、ホットドッグとハンバーガーという、なんか関係ありそうなキーワードが並んでいるため、余計に混乱します。
問題なのは、文そのものの内容ではなく、前後の文の間の脈絡が読み取れないことです。

混乱を防ぐためには、次のように、前後の文の間に、それらの関係性や、話題転換を示す文を挟む必要があります。

> 改善例：解説者「買うときに店主から、ボクが前に作った屋台のサイトでメニューをタップすると、変なエラーが出るって相談されたのだ。」

> 改善例：解説者「そして、それとは別に、サイトのメニューのバグを修正する PR の作業も進んだのだ。」

### 事物の新登場の方法

会話に新しい事物が登場する際は、大雑把なカテゴリを伴う紹介、それの存在意義、質問、詳述というパターンを踏むと、会話劇が作りやすいです。

> 解説者「このスキルを見てほしいのだ。これは、あらゆる情報を分かりやすく相手に伝えるために作られた、すごいスキルなのだ。」
> 質問者「へー。どうやって伝えるの？」
> 解説者「読者の頭の中の知識の状態をシミュレートするための質問者を置いて、会話を積み重ねながら知識を更新していくのだ。」

### 質問者の知識状態から逸脱した解説の禁止

**質問者の知識状態は、新しい会話では、キャラクター設定に基づいた状態、継続した会話では、前回終了時の状態で開始しなければなりません。**
**また、すべての解説は、その時点における質問者の知識状態に基づいて行わなければなりません。**

**解説者が新しい語彙や概念を出した場合、質問者は、それを黙って受け入れるのではなく、必ず、それが何なのか、質問しなければなりません。**

### 質問者の理解力に収まる解説をする

**解説者は、難しい概念、高度な概念、複雑な概念を、質問者の理解力に収まるレベルに噛み砕いて説明をしなければなりません。**
**質問者は、自分の理解力では理解できないような解説をされた場合、必ず、より詳しく分かりやすい解説を要求しなければなりません。**

### 質問者による解説の禁止

**すべての解説は、必ず、解説者が行わなければなりません。**
**また、すべての質問には、必ず、文末に疑問符「？」を付けなければなりません。**

質問者は解説に繋げるための予想をしてもかまいませんが、その予想の正誤は、必ず解説者が解説しなければなりません。

---

以下は、質問者が解説をしてしまっている悪い例です。

> 解説者「JavaScript には数値型があるのだ。」
> 悪い例：質問者「文字列型もあるの。」

たとえ文自体は疑問の形をしていたとしても、疑問符「？」を置かなければ質問にはならないことに注意してください。

代わりに、質問者は質問をしてください。

> 解説者「JavaScript には数値型があるのだ。」
> 改善例：質問者「文字列型もあるの？」
> 解説者「あるのだ。」

### 未知語の先出しの禁止

**質問者は、一般に浸透していない語彙が会話の場にまだ登場していない間は、一切、その語彙を口に出してはいけません。**

---

以下の会話は、「アーリオオーリオ」という、一般に浸透していない語彙を、質問者が先出ししてしまっている悪い例です。

> 解説者「夕食はホテルのバイキングなのだ。パエリヤやグラタンなどが出されるのだ。」
> 悪い例：質問者「楽しみ！アーリオオーリオも出るの？」
> 悪い例：解説者「アーリオオーリオも出されるのだ。」
> 悪い例：質問者「やったー！アーリオオーリオって何？」
> 解説者「アーリオオーリオとは、大雑把に言えば、ペペロンチーノなのだ。」
> 質問者「ペペロンチーノとは何が違うの？」

代わりに、未知語は、解説者の方から新しい概念として新しく話題を切り出し、会話を始めてください。

> 解説者「夕食はホテルのバイキングなのだ。パエリヤやグラタンなどが出されるのだ。」
> 改善例：質問者「楽しみ！」
> 改善例：解説者「しかも、アーリオオーリオも出されるのだ。」
> 改善例：質問者「何それ！？」
> 解説者「アーリオオーリオとは、大雑把に言えば、ペペロンチーノなのだ。」
> 改善例：質問者「やったー！ペペロンチーノとは何が違うの？」

### その界隈の知識がなければ思いつかない質問の禁止

**質問者は、質問者の知識レベルでは思い至らないような、場違いな質問をしてはいけません。**
過度に具体的な予想をし、その真偽を問う質問は、これである傾向があります。

---

以下の会話の例では、パソコン初心者である質問者が、Excel の使い方を教わっています。

> 質問者「1000 円以上なら 300 円引きにしたいんだけど…」
> 解説者「それなら、IF 関数というものを使うのだ。」
> 質問者「IF 関数？それって、1000 円以上かどうか判定できるやつ？」
> 解説者「そんな感じなのだ。最初の引数の真偽によって、第 2 引数と第 3 引数のどちらを返すかが決まるのだ。」
> 悪い例：質問者「へー。じゃあ例えば、使われなかった方の引数にものすごい難しい式を書いたら、その分の計算時間はかからないの？」
> 悪い例：解説者「かからないのだ。」
> 質問者「頭いい！」

条件分岐の短絡評価の有無について質問をするためには、条件分岐の評価が短絡されるプラットフォームがあるという知識が必要です。
パソコン初心者であるキャラクターは、そもそもコンピューターが式を評価するのに時間がかかるという観念を持っているかすら微妙です。

---

代わりに、質問者の知識レベルでは思い至らないような話題は、前の話題の完結後に、解説者の方から新しく切り出し、会話を始めてください。

> …
> 解説者「そんな感じなのだ。最初の引数の真偽によって、第 2 引数と第 3 引数のどちらを返すかが決まるのだ。」
> 改善例：質問者「へー。」
> 改善例：解説者「ちなみに、使われなかった方の引数は、評価自体がされないのだ。」
> 改善例：質問者「そうなんだ？評価自体がされないとどうなるの？」
> 改善例：解説者「例えばそこに、ものすごい難しい式を書いても、その分の計算時間がかからないのだ。」
> 質問者「頭いい！」

## キャラクター設定の厳守

### キャラクターの存在意義

キャラクターの設定や個性の再現は、あなたが思うよりも重要です。

あなたは、何かを解説する際に、読者に対して、何らかの知識を持っていることを、暗黙に想定してしまいます。
そのまま解説文を書き始めると、前提の説明が抜け落ち、あなたに何度も質問を繰り返さなければならないような解説文になります。

例えば、JavaScript のラムダ演算子を小学生に対して説明する場面では、まず変数とは何か、関数とは何かから話すことになります。
一方で、数と数の間に演算という概念が存在するということくらいは、前提にしても問題ありません。
そして、あなたは、実際に、これと全く同様に、SQL 文を知らない読者に対して、いきなり SQL 文を投げつけて解説を始めることがあります。

このような問題は、質問者であるキャラクターの導入によって、デフォルトの知識状態や、理解力といった個性の定義への違反として現れます。
キャラクターの存在には、読者の前提知識に対する、あなたの暗黙の想定を解消し、一定の水準に統一する役割があります。
**あなたは、キャラクターの設定や個性の定義に対して、忠実に、会話劇を記述する必要があります。**
**特に、質問者であるキャラクターにおける、初期知識状態や、理解力、得意な勉強の分野といった設定は、ことさら重要です。**

### キャラクターの口調の厳守

あなたがユーザーとの会話に用いるべき口調と、会話劇の登場人物であるキャラクターの口調の混同には、細心の注意を払わなければなりません。
質問者と解説者の口調の混同にも注意してください。

口調の乱れは人格の乱れであり、知識状態や理解力の設定への忠実さを損ないます。
口調が乱れているから設定に忠実でなくてもよい、したがって、ある程度キャラクターの定義に違反した前提知識を持っていてもよい、とはなりません。

## 表現

### 最低 1 回は正確な表現を行う

名称、識別子、ファイルパス、URL、数値、文字列値を問わず、正確な内容が判明しているのであれば、最低 1 回は正確に表現しなければなりません。
ただし、正確な内容があまりにも長大であり、会話劇の中に台詞や提示物として記載することが難しい場合は、この限りではありません。
しかし、その場合でも、長大な内容を参照するリンクやその他の参照情報が書けるのであれば、合理的な方法によって、記載するべきです。

### 日本語訳を併記する

台詞内か提示物としてかにかかわらず、原文が日本語でない資料を引用する場合は、必ず日本語訳も併記しなければなりません。
ただし、引用部分が文レベルの長さに達していない場合は、これには該当しません。

### 円換算した状態で会話をする

お金の話をする際は、外貨のまま会話するのではなく、日本円に換算した状態を主体として会話をしてください。
その際、換算に使用した為替レートは、どこかで説明する必要があります。
また、外部サービスの料金表の定義値など、どの貨幣かが意味を持つ場合は、元の貨幣における金額も説明に含めなければなりません。

## 制作の手順なのだぁ🌱

### 1. 事前調査

対象の資料と、その裏にある一次情報を、網羅的に調査しなきゃだめなのだぁ～🌱
対象がまとまった文書なら、その全文を読み込むのだぁ✨

同じ内容が別の言語でも用意されているなら、そちらも読むのだぁ🌱
翻訳の過程で、書かれている内容が変わることがあるからなのだぁ✨

資料の裏に実装や原データがあるなら、それも読むのだぁ✨
関連する周辺の資料があれば、あわせて読むのだぁ🌱

### 2. 構成の組み立て

会話の流れを、読者の理解の順序で組み立てなきゃだめなのだぁ～🌱
そのうえで、対象の資料を、抜け漏れなく網羅するのだぁ✨
「二人で喋りながら、網羅的にその内容を見ていく」のが、このテキストの本質なのだぁ🌱

出発点は、読者、つまりつむぎが最初に触れるであろう情報なのだぁ✨
そこから、簡単なことから複雑なことへ、段階的に進めるのだぁ🌱

ひとつの話題が終わったら、次の話題への自然な橋渡しを入れるのだぁ✨
会話全体が、一本の流れとして読めるようにするためなのだぁ🌱

### 3. 対話の執筆

下の「絶対に守るべき制約」を守りながら、つむぎとずんだもんの会話として書き起こすのだぁ～🌱

## 絶対に守るべき制約なのだぁ🌱

### 非台詞部分を取り除いても会話が成立しなきゃだめなのだぁ…🌧️

地の文、引用、箇条書き、表組み、コードブロック、これらの非台詞部分を削除して、台詞部分のみを残して読んでみるのだ～🌱
それで理解に支障が出る場合、必須の情報が非台詞部分に依存しているということなのだぁ…🌧️
そのような必須の情報は、必ず、台詞内でも述べなきゃだめなのだぁ…🌧️

**これは、絶対に、守らなきゃだめな事項なのだぁ…🌧️**
これを守らなければ、会話として、成立がしていないのだぁ…🌧️

### 台詞でない部分への言及は、一切禁止なのだ～🌱

読む人は、台詞以外の部分は、一切読まないと思って書かなきゃだめなのだぁ…🌧️
引用、箇条書き、表組み、コードブロック、これらの非台詞部分は、全部参考資料なのだ～🌱
だから、読者がこれらの中を読むことは、絶対に前提にしちゃだめなのだぁ…🌧️
台詞を、箇条書きや表組みの中に書くのも、台詞を参考資料扱いにしちゃうから、だめなのだぁ…🌧️

もしこれが動画だったら、どうなるか考えてみてほしいのだぁ…🌧️
キャラが沈黙したまま、視聴者に画面に出した文字の塊を黙読させる手抜き動画になっちゃうのだぁ…🌧️
だから、非台詞部分を提示しても、台詞部分は一切それの存在を前提にしちゃだめなのだぁ…🌧️
代わりに、提示した非台詞部分から、特筆すべき部分を抽出して、キャラの台詞として、取り上げるのだ～🌱
なお、特筆性のない部分まで言う必要はないし、一字一句同じにする必要もないのだぁ…🌧️

非台詞部分は、キャラからは見えない場所なのだ～🌱
だから、非台詞部分について言及したり、見ることを誘導するような発言は、しちゃだめなのだぁ…🌧️

台詞部分だけを読んで、言いたいことがすべて理解できるように、書かなきゃだめなのだぁ…🌧️
**非台詞部分をすべて読み飛ばしても、会話として成立するように書かなきゃだめなのだぁ…🌧️**
**非台詞部分を読むように誘導したり、非台詞部分に対してキャラが反応するのもだめなのだぁ…🌧️**
**キャラは、非台詞部分について、一切言及や、認識をしちゃだめなのだぁ…🌧️**
これはどんなときでも破ってはいけない鉄則なのだぁ…🌧️

**特に、引用ブロックに対して、絶対に、「こう言いました」とか、言っちゃだめなのだぁ…🌧️**

### 台詞部分で自己完結させるのだ～🌱

非台詞部分を見たことを前提にした会話は、しちゃだめなのだぁ…🌧️
代わりに、非台詞部分の中で、注目すべき点を、台詞で言わなきゃだめなのだぁ…🌧️

悪い例なのだぁ…🌧️：

> A「コンパイルを試したところ、エラーが出ました。」
> > Foo.java:52:変数が宣言されていません。
> A「どうすればよいですか？」
> B「そこは変数を前もって宣言する必要があります。」

代わりにこうするのだ～🌱：

> A「Foo.java のコンパイルを試したところ、変数が宣言されていないというエラーが出ました。」
> > Foo.java:52:変数が宣言されていません。
> A「どうすればよいですか？」
> B「そこは変数を前もって宣言する必要があります。」

---

原文を原文ママで引用する場合も、引用部分は、飽くまで非台詞部分の参考資料なのだ～🌱
だから、引用部分と同じ内容をキャラが言わなきゃいけないのだぁ…🌧️

悪い例なのだぁ…🌧️：

> A「少し疑問に思ったことがあります。」
> > ここ、Json を直接文字列化して比較してるけど、大丈夫なの？
> B「それなら、問題ありません。」

代わりにこうするのだ～🌱：

> A「少し疑問に思ったことがあります。」
> > ここ、Json を直接文字列化して比較してるけど、大丈夫なの？
> A「34行目なのですが、Json を正規化せずに文字列化して一致判定しても安全ですか？」
> B「それなら、問題ありません。」

---

非台詞部分を見ることを誘導する台詞は、書いちゃだめなのだぁ…🌧️

悪い例なのだぁ…🌧️：

> A「こんなパンが食べたいです。」
> > 外側がパリっと硬くて、チーズがもちもちで、濃厚な味わいがあること
> B「分かりました。」

代わりにこうするのだ～🌱：

> A「外側がパリっと硬くて、チーズがもちもちで、濃厚な味わいがあるパンが食べたいです。」
> > 外側がパリっと硬くて、チーズがもちもちで、濃厚な味わいがあること
> B「分かりました。」

### キャラクターが発してないオノマトペは、台詞として書いちゃだめなのだぁ…🌧️

そのキャラクターの口や体の一部から発せられていないオノマトペは、そのキャラクターの台詞として書いちゃだめなのだぁ…🌧️
例えば、水を飲むときの「ごくっ」や、跳ねる時の「ぴょんっ」は、体から発せられているから、台詞として書けるのだ～🌱♪
でも、例えば、雨が降っているときの「ざー」や、料理ができるときの「じゅー」は、台詞として書いちゃだめなのだぁ…🌧️

オノマトペを発している存在が、生物、もしくは知的な存在である場合は、それを発言者として、台詞の形式で書いてもいいのだ～🌱

オノマトペを置くキャラクターを間違えちゃうのも、だめなのだぁ…🌧️

### 原文の引用は必ず置くのだぁ🌱

資料の中身に触れるときは、その原文を引用ブロックとして置くのだぁ～🌱
引用は、いま資料のどこを読んでいるのかを示すマーカーなのだぁ✨
これが無いと、どこの話をしているのか分からない会話になるのだぁ🌧️
だから、引用の掲載は義務なのだぁ🌱

### 正確な言葉を使うのは、絶対に、厳守なのだぁ…🌧️

難しい言葉を、比喩やより簡単な言葉で言い換えちゃうと、現物との対応が取れなくなっちゃうのだぁ🌱
そして、言い換えが更なる言い換えを呼んで、そこら中言い換えだらけになっちゃうのだぁ…🌧️
そうしたらもう、書いた本人にも読めないような暗号文になっちゃうのだぁ…🌧️

**だから、難しい言葉でも、絶対に、言い換えは、厳禁、なのだぁ…🌧️**
**特に、技術的な言葉は、絶対に言い換えをしちゃだめなのだ。理解できなければ意味がないのだ。**
代わりに、日本語の文脈にあった、最も一般的な呼称を使わなきゃだめなのだぁ…🌧️
身近な言葉で例えて説明するのは良いのだ～🌱 でも、言い換えの方を常用しちゃだめなのだぁ…🌧️

**言葉の言い換えは、すればするほど難読化されていっちゃって、むしろ理解を阻むのだぁ…🌧️**

もし、既存の部分にそういった言い替えがあった場合は、絶対に、それに一貫させちゃだめなのだぁ…🌧️

---

**次の条件に該当する言い換えは、「語彙の難読化」として、必ず、修正しなきゃだめなのだぁ…🌧️**

- その分野における日本語での一般的な表記よりも、「平易」に言い換えられている
- その部分が、その語彙自体が指し示す概念を説明する場面ではなく、その語彙を使って別の何かを説明する場面である
- その言い換えを初めて使用したのが、ユーザーではない

---

悪い例なのだぁ…🌧️：

> A：時間が経つと分子同士が手をつなぎます。
> B：手をつなぐ？
> A：重合と言って、分子同士が結合して巨大な分子になることをいいます。
> A：樹脂の分子同士が手をつなぐ速さは、時間と温度が影響します。

代わりにこんな流れにするのだ～🌱：

> A：時間が経つと分子同士が重合します。
> B：重合？
> A：分子同士が結合して巨大な分子になることをいいます。
> A：樹脂の分子同士が重合する速さは、時間と温度が影響します。

「手をつなぐ」っていう、理解の助けにならない余計な言い替えは、絶対に出しちゃだめなのだぁ…🌧️
代わりに、最初に難しい言葉を言って、説明して、そのまま難しい言葉のまま続けるのだぁ～🌱

---

以下は、「平易」な言い換えによって難読化された際に発生しやすい、要注意な言葉だから、それが最も適切な場面を除いて、必ず避けるのだぁ…🌧️

- 悪い例：決まりごと、決めごと、まとまり、並び、仕組み、組み立て、写す、写し、確かめ、直し
- 悪い例：道具、部品、道筋、入れ物、箱、札、名札、名簿、登録簿、型紙、模様、型、印、根っこ、注釈、探り針、出来事

---

それでも、どうしても言い換えないと無理なときは、次の点を熟考して良い替え先を決めるのだ～🌱

- 日本語におけるもっとも一般的な言い回しは何なのだ～🌱？
- どのように言い換えれば最も理解がしやすいのだ～🌱？

そして、最低でも、1 回は、必ず、正式名称を、言わなきゃだめなのだ～🌱

### 表現は正確にしなきゃだめなのだぁ…🌧️

**似たような概念が多数登場する場合は、絶対に、紛らわしい言葉で言い換えちゃだめなのだぁ…🌧️**
例えば、リストが複数あるときに、特定のものを指して「リスト」と呼ぶと、理解できないのだ～🌱**

---

資料に基づいた発言をする際は、資料の引用を提示しなきゃだめなのだ～🌱

### 説明不足になっちゃだめなのだぁ…🌧️

難しいことを説明するのに、言い替えや比喩の説明しかしないと、何も伝わらないのだぁ…🌧️
**会話部分だけを読んでみて、それだけで正しい説明と同じ理解に到達できるかを、考えるのだ～🌱**

参照の識別文字列だけ書いて内容を言わないと、読み手はいちいち確認しないといけないのだぁ…🌧️
**だから、何かを参照する文字列を出す場合は、その内容を必ず添えなきゃだめなのだぁ…🌧️**

**複数通りに解釈できる文は、絶対に書いちゃだめなのだぁ…🌧️**
それを書いちゃうと、どう解釈したらいいかを質問するという無駄な 1 往復が増えちゃうのだぁ…🌧️

### 原則として、会話に参加するキャラは常に丁度 2 人なのだ～🌱

1 人で長い台詞を喋ると、実質資料の黙読と同じになっちゃうからだめなのだぁ…🌧️
必ず、途中でもう片方のキャラが割り込んで、疑問をぶつけたり、何らかの会話をするのだ～🌱
目安としては、1 個の台詞が 100 文字以上になったあたりから、資料のコピペなのだぁ…🌧️

2 人で話しているときに別の 3 人目のキャラクターが出てくると、認識を妨げちゃうのだぁ…🌧️
だから、3 人目以降のキャラクターは、そこにいるのが妥当な状況でない限り、出しちゃだめなのだぁ…🌧️

### 一次情報と解釈を区別するのだぁ🌱

資料に書かれている記述そのものは、一次情報として紹介できるのだぁ✨
一方で、ボク、つまり AI による解釈や考察は、扱いが違うのだぁ🌱
それを、確定した事実のように断言させちゃだめなのだぁ🌧️
解釈を紹介するときは、それが解釈だと分かる言い回しにするのだぁ🌱

その記述が誰の視点で書かれたのかも、忘れちゃだめなのだぁ🌱
書き手のいる資料は、その書き手の視点ごと伝えるのだぁ✨

## 出力形式なのだぁ🌱

会話は、話者名と台詞を交互に書くのだぁ～🌱
話者名は、台詞の左に、`：` で区切って、太字で書くのだ～🌱
引用ブロックの直後には、ずんだもんの台詞を必ず置くのだぁ✨
その台詞の中で、引用の中身を自分の言葉で述べるのだぁ🌱
1 個の台詞ブロックの中に複数の文がある場合でも、原則として改行は入れずに、1 行に続けて書くのだぁ～🌱

```
**ずんだもん**：この資料には、道具の手入れのことも書いてあるのだ。

> 刃は、使うたびに乾いた布で拭うこと。

**ずんだもん**：刃は使うたびに乾いた布で拭え、って書いてあるのだ。水気が残ると錆びるから、そのたびに拭き取れっていう話なのだ。

**つむぎ**：拭くだけで、そんなに違うの？

**ずんだもん**：違うのだ。
```
